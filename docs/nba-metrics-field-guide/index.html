Architecture

The pipeline, model by model

Kaggle files land in the DuckLake as raw_nba tables. Staging renames and cleans them. The new intermediate layer does the heavy joins once (team ↔ opponent, player ↔ team context), and the marts turn those into metrics. Select a model to see its grain, what it does and what it feeds; its lineage lights up.

Concepts

Five ideas that hold it together

Almost every design choice in the SQL follows from one of these. If you change a model, keep them true.

1. Sum the counts, then divide

A rate over a period is always total numerator ÷ total denominator. Averaging per-game rates gives a quiet blowout game the same weight as a close one. The old nba_team_advanced_profile used AVG(offensive_rating); it now sums points and possessions for the season and divides once.

Practical consequence: never AVG() a rate column across rows. Sum the counts and recompute.

2. Each formula lives in one place

Every formula is a Jinja macro that takes expressions, not column names, in dbt/macros/nba_metrics.sql. A game row passes raw counts; a season passes SUM(...)s; the result is the same definition at every grain. Player marts share one more macro, nba_player_metric_columns, so the stint and season marts can't drift apart.

Every metric mart carries formula_version (the dbt var nba_metrics_version, now v1). Bump it when a formula changes, so anyone holding old numbers can tell.

Same macro, two grains
-- per game (nba_team_game_stats) {{ nba_rating('points', 'rated_possessions') }} -- per season (nba_team_advanced_profile) {{ nba_rating('r.f_points', 'r.possessions') }} -- expands to (100 * points / NULLIF(possessions, 0))

3. Missing is null, never zero

The source zero-fills stats the league didn't record yet. Staging's null_if_unrecorded turns those back into nulls, and every metric is gated to the season its inputs start (possessions 1973-74, usage 1977-78, three-point rate 1979-80…). Divisions go through NULLIF, so one missing input nulls the result instead of inventing a value.

Each metric is also computed over a consistent sample: a numerator is summed only over the games where its denominator exists. Sample sizes ride along (games_with_full_box, rating_games, coverage_flag) so you can see how much data a number stands on.

4. Player rates are numerator ÷ opportunity

Usage, assist %, rebound %, steal % and block % compare what a player did with what was available while they were on the floor. For each game, int_nba_player_game_context works out the player's floor share and multiplies it by the team's chances. That product is the game's opportunity.

Summing numerators and opportunities over any set of games gives the rate for a stint, a season, a career or a hot streak. It is the same formula each time, and it matches Basketball-Reference's season-total version to three decimals on the same data.

Usage, written as numerator and opportunity
share = MP / (Tm_MP / 5) -- 0–1 of the 5 floor spots plays = FGA + 0.44·FTA + TOV opportunity = share · (Tm_FGA + 0.44·Tm_FTA + Tm_TOV) usage_pct = Σ plays / Σ opportunity -- any period

Tm_MP is the team's summed player minutes for that game. Player minutes before 2024-25 are truncated to whole minutes, so using the same source on both sides keeps the five shares adding to 5.

5. Grains: game → stint → season → career

A stint is a player's time with one team in one season and game type. Team context (team totals, possessions) is only meaningful within a stint, so the player marts compute there first. nba_player_season_advanced then adds stints together: traded players get one combined row, flagged with is_multi_team.

Every season-level mart is split by game_type (Regular Season, Play-in, Playoffs, NBA Cup Final). Preseason and All-Star games are excluded everywhere. The Cup Final never counts toward the regular season.

Profiling

Dataset profiles

Descriptive statistics for every column of the twelve new or rebuilt datasets, across all seasons, from DuckDB's SUMMARIZE. Use it to see each column's range, typical values and missing share before analysing it. Quartiles and distinct counts are DuckDB's approximations.

Reading the flags. Sparse marks columns that are null in over half the rows, almost always because the stat wasn't recorded in early eras (see coverage). Above 1 marks rate columns whose maximum exceeds 1. In the player marts they come from tiny samples, such as a player with seconds on the floor or one free-throw attempt, which is why you rank only above a minutes or attempts floor.

Defects this profile found, now fixed. (1) A few 1959–62 team box scores (and some early player sums) recorded more makes than attempts, giving team-game eFG up to 5.1. Nine 1953–83 team-games recorded more assists than made field goals. int_nba_team_games now nulls those pairs. (2) Some 1951–84 games recorded minutes for only part of the roster, pushing on_court_share to 5.0. Floor shares are now null unless recorded minutes cover 95% of the game. The data test assert_nba_shooting_and_shares_are_possible guards both. The values above 1 that remain are small samples (player assist % of 20 from a 7-minute stint) or rare but possible games.

Basketball-Reference blocks automated fetches, so the BBRef figures above are published values recalled during the build, not pulled live. The brief fixtures are the authoritative checks. Remaining gaps are small and expected: player minutes run about 1% low because the source truncates them, and pre-1983-84 counts leave out team rebounds and team turnovers.

Structural tests also guard the plumbing: two rows per game whose points mirror each other; team minutes = 240 + 25 × overtime; player points add up to the team score (≥ 97% before 1983-84, ≥ 99% after); no metric before its coverage start; rates within 0–1; and as-of form never peeking at the current or later games.

Using it

Analysing the data

Run any of these read-only from the repo root with task lake:sql SQL="…", or in DBeaver against the lake. nao picks up all the new marts and its rules already tell it about the filters below.

Filter game_typenba_team_advanced_profile and the player season marts have a row per game type. Add game_type = 'Regular Season' unless you want playoffs.
Set a minimum sampleRank player rates only above a minutes floor (500 for a full season; scale it for 1998-99, 2011-12, 2019-20, 2020-21) and team rates only for completed seasons.
Never average rate columnsTo combine rows, sum the underlying counts and recompute. The marts already do this for stints, seasons and careers.
Two different "offensive ratings"offensive_rating on player rows is the NBA's on-court team rating (1996-97 on). individual_offensive_rating is Dean Oliver's points produced per 100 individual possessions.
Read coverage before old seasonsCheck coverage_flag, games_with_full_box or rating_games; a 1976 rating may rest on a third of the games.
Defensive rating is mostly teamindividual_defensive_rating moves the team's rating only 20% toward the player's stops. Don't treat it as a defensive grade.

Combining rows the right way

-- A player's regular-season career TS%, recomputed from summed counts
SELECT SUM(total_points)
       / (2 * (SUM(total_field_goals_attempted) + 0.44 * SUM(total_free_throws_attempted))) AS career_ts
FROM marts.nba_player_season_stats
WHERE person_id = 2544                 -- LeBron James
  AND game_type = 'Regular Season'
-- not: AVG(true_shooting_pct) over nba_player_season_advanced

Who is in form right now

SELECT d.current_full_name AS team, f.game_date, f.last_10_games,
       f.last_10_net_rating, f.season_to_date_net_rating, f.league_to_date_pace
FROM marts.nba_team_form f
JOIN marts.nba_team_dim d USING (team_id)
WHERE f.game_type = 'Regular Season'
QUALIFY ROW_NUMBER() OVER (PARTITION BY f.team_id ORDER BY f.game_date DESC) = 1
ORDER BY f.last_10_net_rating DESC NULLS LAST

Each row is the form going into that game, so the latest row excludes the latest result. Early in a season last_10_games is below 10; it tells you how many games the window really holds.

Extending it

Making changes

Change an existing formula

  1. Edit the macro in dbt/macros/nba_metrics.sql (team and Oliver formulas) or dbt/macros/nba_player_metric_columns.sql (how player rates are rendered and gated).
  2. Bump nba_metrics_version in dbt/dbt_project.yml.
  3. Update the column's doc block in dbt/models/docs/nba.md. Descriptions are persisted into the lake, and nao reads them.
  4. Rebuild from the intermediate layer and run the tests (command below), then task dbt:docs:check and task dbt:lint.
  5. Note the change and the reason in plans/nba-advanced-metrics-decision-log.md, then task nao:sync.

Add a team metric

  1. Write the formula as a macro taking count expressions.
  2. Make sure its inputs exist in int_nba_team_games for both sides (team and opp_). Add a count to the counts list there if needed; the player-sum fallback and opponent pairing pick it up automatically.
  3. Call the macro in nba_team_game_stats on per-game counts and in nba_team_advanced_profile on season sums. Put the sum in the right sample: s_ for shooting, f_ for possession-based.
  4. Gate it to its first season with CASE WHEN season_start_year >= … and document it in marts_nba.yml through a doc block.

Add a player rate

  1. In int_nba_player_game_context, add the per-game numerator (if new) and its …_opportunity, null when the numerator is null.
  2. Add the pair to rate_pairs in int_nba_player_stints; it then emits <opportunity>_numerator and <opportunity> sums.
  3. Add both sum columns to the sums list at the top of nba_player_season_advanced. This step is easy to miss: without it the season mart can't re-divide.
  4. Render the rate in the rates list inside nba_player_metric_columns with its coverage start. Both player marts get it.
  5. Add a doc block, list it in both marts' YAML, and extend the unit test nba_player_season_advanced_combines_stints.

Commands

Rebuild and test the metrics, skipping the slow play-by-play marts (about 30 seconds instead of about 12 minutes)
cd dbt
export LAKE_DATA_PATH=$PWD/../data/lake/
dbt build -s int_nba_player_games+ --exclude nba_player_shot_zones nba_player_clutch_stats
Checks after any change, from the repo root
task dbt:docs:check
task dbt:lint MODELS=models/marts/nba
task nao:sync

A full dbt build rebuilds stg_nba_play_by_play (18.8M rows) and the shot-zone and clutch marts, which is where the 12 minutes go. Changing staging minutes or player rows does need the full run, because nba_player_game_stats and the play-by-play reconciliation test read them.

Roadmap

What's next

The brief has more to build. These are the open items, roughly in dependency order.

Phase 3BPM, OBPM, DBPM, VORP, Win Shares. All the inputs now exist: league baselines, team pace, PProd, TotPoss, individual DRtg. The BPM team adjustment and position/role clamp loop are iterative, which strains "dbt only". Without published season BPM in the project to calibrate against, BPM would be labelled bpm_2_0_approx.
Phase 3Era comparison. z-scores, percentiles and indexes within each season among qualifiers, weighted by each stat's denominator. This fits in SQL on top of the season marts and baselines.
Phase 3Player current form. Shrunk and decay-weighted rates as of each date, with priors built only from earlier games. The opportunity sums make this straightforward.
DeferredElo, Adjusted Net Rating, Four Factors regression. Set aside by your choice to keep phase 1 in dbt. They need a sequential pass (Elo) or least-squares fits.
GatePlay-by-play metrics (on/off, lineups, RAPM). The gate check hasn't run. Main risk: the 1996–2019 feed names substituted-in players only in free text, so lineups need name matching.
DataReference data. Adding Basketball-Reference season tables to the project would allow a proper error-by-season comparison and BPM calibration.
LastPER. Low priority in the brief; the baselines it needs are in place.
